# How this profile generates itself

Everything on this page is drawn by files in this repo — no third-party
stats cards, no external image services. Two pieces:

## 1. The portrait — `first.svg`

Built by `make_ascii_svg.py` from a headshot (not committed — see the
script's docstring/comments for the pipeline: `rembg` cutout, bilateral
filter, CLAHE, a `(v/255)^1.7` darkening curve, then mapped to the ramp
`" .`:-=+*cs#%@"`). Each row types in via a `clipPath` + SMIL `animate`,
staggered `0.09s` per row, `fill="freeze"` so it plays once.

To regenerate after swapping the source photo:

```bash
pip install pillow numpy opencv-python-headless rembg onnxruntime
python3 make_ascii_svg.py path/to/headshot.jpg first.svg
```

## 2. Live stats — `stats.svg`, `streak.svg`, `langs.svg`, `year.svg`

Generated by `scripts/generate_stats.py`, which talks to the GitHub
GraphQL API using **only the standard library** (`urllib`), so there is
nothing to break in CI. It:

- pins the contribution window to whole UTC days (`00:00:00Z` →
  `23:59:59Z`), so two runs minutes apart never bucket a day into a
  different week and shift the sparkline
- filters `repositories(privacy: PUBLIC)`, so the workflow's built-in
  `GITHUB_TOKEN` and a personal token report identical language stats
- draws contribution weeks as columns, not a line — a zero week is empty
  space, not a claimed value between two points that never existed
- reuses the portrait's own ramp for `year.svg`, one cell per day

Run locally against your own account:

```bash
GH_LOGIN=<your-username> GITHUB_TOKEN=<token with read:user scope> \
  python3 scripts/generate_stats.py
```

### The workflow — `.github/workflows/refresh-stats.yml`

Runs nightly (`17 5 * * *` UTC) plus `workflow_dispatch`, with **no**
`push` trigger — this job commits, and a push trigger would re-run it on
its own commit. It only commits when the generated SVGs actually change,
so there isn't a meaningless nightly commit stream. No personal access
token is needed; the built-in `GITHUB_TOKEN` is enough to read public
contribution/repo data for the repo owner.

## 3. Text on the page

GitHub's markdown sanitiser strips `<style>`, `style="..."`, `class="..."`,
inline `<svg>`, `<font>`, `<small>`, `<big>`. What survives: `<sub>` `<sup>`
`<kbd>` `<samp>` `<blockquote>` `<details>` `<hr>` `<picture>`, and
`align=`/`width=` on `<img>`/`<td>`. So:

- `samp` is used instead of backticks where a stack row shouldn't get the
  boxed-chip background
- a `blockquote`/`sub` is used for asides, which gets a rule + dimmer text
  for free, no CSS required
- there is no way to change the README body font — that's a GitHub
  limitation, not something this pipeline works around

## 4. Font inlining (optional) — `scripts/subset_font.sh`

If you want the *portrait and stats SVGs themselves* (not the README
body — see above) to render in JetBrains Mono everywhere rather than
whatever monospace a visitor's OS picks: an external font URL cannot work
here, because these SVGs load through an `<img>` tag and browsers refuse
subresource fetches for image documents. The font has to be a base64
`@font-face` data URI baked directly into each SVG.

`scripts/subset_font.sh` subsets JetBrains Mono (SIL OFL) into three tiny
per-role `woff2` files — a 13-character ramp subset for the portrait, a
heading-letters subset, and a basic-Latin subset for the data graphics —
base64-encodes each into `fonts/*.b64`, and `generate_stats.py` picks
those up automatically if present (see `_embedded_font_face` in that
script). Total added weight is on the order of tens of KB across the
whole page, versus a few MB for inlining the full TTF everywhere.

This step needs the source TTF, which isn't vendored here to keep the
repo small — see the comments at the top of `scripts/subset_font.sh` for
where to get it. Ship `fonts/OFL.txt` alongside if you do this; the
license has to travel with the font file since it lands in a public repo.

## Gotchas

- A full-page headless-Chrome screenshot (`fullPage: true`) restarts the
  SMIL animation and produces a blank portrait — use a tall viewport and
  wait instead.
- A newly created/edited profile README can be cached; edit it once
  through the GitHub web UI if it doesn't show up.
- Test any markdown changes against `POST /markdown` before committing —
  it applies the same sanitiser GitHub uses on the live page.
